1. DOM 직접 제어의 한계

Day 3까지 우리는 JavaScript로 DOM을 직접 제어했다.

title.textContent = count;
title.style.color = "red";

이 방식은 작은 화면에서는 문제가 없지만, 화면이 조금만 복잡해져도 관리 비용이 급격히 증가한다.

DOM 직접 제어의 문제점

  • 같은 DOM 조작 코드가 여러 곳에서 반복된다
  • 데이터(상태) 변경 코드와 화면(DOM) 변경 코드가 섞인다
  • 화면 구조가 바뀌면 JavaScript 코드도 함께 수정해야 한다

👉 DOM을 직접 만지는 방식은 규모가 커질수록 유지보수가 어렵다.

2. DOM 직접 제어 실습

실습 목표

  • "상태가 바뀌어도 화면은 자동으로 바뀌지 않는다"는 사실을 체험한다
  • 상태 로직과 화면 로직이 섞이기 시작하는 지점을 직접 확인한다

실습가이드

📄 파일명: 2-dom-hard.html

<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8" />
  <title>DOM 직접 제어 실습</title>
</head>
<body>

  <p id="count">0</p>
  <button id="btn">증가</button>

  <script>
    let count = 0;

    const countEl = document.getElementById("count");
    const button = document.getElementById("btn");

    button.addEventListener("click", handleClick);

    function handleClick() {
      // Step 코드가 이 함수 안에 추가된다
    }
  </script>

</body>
</html>

사전 체크

  • 버튼 클릭 시 handleClick 함수가 실행되는지 확인한다
  • 아직 화면 숫자는 바뀌지 않는다

Step 1. 상태 값 증가 처리

count = count + 1;

체크 포인트

  • 클릭할 때마다 count 값은 증가한다
  • 화면 숫자는 여전히 0이다
  • 상태와 화면은 자동으로 연결되지 않는다

Step 2. 숫자 화면 반영

countEl.textContent = count;

체크 포인트

  • 상태 변경 결과를 직접 DOM에 반영해야 한다
  • 화면 갱신 책임이 개발자에게 있다

Step 3. 화면 스타일 변경

if (count % 2 === 0) {
  countEl.style.color = "red";
} else {
  countEl.style.color = "blue";
}

체크 포인트

  • 상태 값에 따라 화면 스타일을 직접 제어한다
  • 상태 로직 + 화면 로직이 한 함수에 섞이기 시작한다

실습 정리

  • 데이터가 바뀌어도 화면은 자동으로 바뀌지 않는다
  • 화면 변경을 위해 항상 DOM을 직접 조작해야 한다
  • 로직이 커질수록 코드가 빠르게 복잡해진다

👉 이 구조가 프레임워크 등장 배경이다

3. 도구의 진화

3-1. jQuery

jQuery는 DOM 조작을 쉽게 만든 도구다.

  • DOM 선택과 조작을 간결한 문법으로 제공
  • 코드량은 줄어들지만 DOM 직접 제어 구조는 그대로 유지된다

jQuery 실습

📄 파일명: 3-jquery-basic.html

<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8" />
  <title>jQuery 기본 실습</title>
</head>
<body>

  <p id="count">0</p>
  <button id="btn">증가</button>

  <script src="https://code.jquery.com/jquery-3.7.1.min.js"></script>
  <script>
    let count = 0;

    $("#btn").on("click", handleClick);

    function handleClick() {
      count = count + 1;
      $("#count").text(count);

      if (count % 2 === 0) {
        $("#count").css("color", "red");
      } else {
        $("#count").css("color", "blue");
      }
    }
  </script>

</body>
</html>

체크 포인트

  • 문법은 편해졌지만 구조는 동일하다
  • 상태 변경 → DOM 직접 수정 흐름은 변하지 않는다

3-2. Vue / React

Vue와 React는 DOM을 직접 만지지 않는다.

  • 화면 기준은 DOM이 아니라 상태(State)
  • 상태가 바뀌면 화면은 자동으로 갱신된다
  • DOM 관리는 프레임워크가 담당한다
구분 흐름
jQuery DOM → 화면
Vue / React 상태 → 화면

4. Vue3 Composition API 맛보기 (CDN 방식)

실습 목표

  • Vue가 DOM을 직접 제어하지 않는 방식을 체감한다
  • "상태만 바꿨는데 화면이 바뀐다"는 경험을 한다
  • DOM 조작 코드가 사라지는 구조를 확인한다

실습가이드

📄 파일명: 4-vue-cdn.html

<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8" />
  <title>Vue CDN 실습 (Composition API)</title>
</head>
<body>

  <div id="app">
    <p>{{ count }}</p>
    <button @click="increase">증가</button>
  </div>

  <script src="https://unpkg.com/vue@3/dist/vue.global.js"></script>
  <script>
    const { createApp, ref } = Vue;

    createApp({
      setup() {
        const count = ref(0);

        const increase = () => {
          count.value++;
        };

        return { count, increase };
      }
    }).mount("#app");
  </script>

</body>
</html>

Step 1. Vue가 관리할 화면 영역 이해

  • <div id="app"> 영역을 Vue가 전담 관리한다
  • 이 영역 안에서는 DOM을 직접 건드리지 않는다

체크 포인트

  • document.getElementById가 없다
  • addEventListener가 없다

Step 2. 상태(State) 정의

  • setup() 함수 안에서 ref()로 상태를 만든다
  • count는 Vue가 추적하는 반응형 상태다

체크 포인트

  • 실제 값은 count.value에 들어 있다
  • 이 값이 화면의 기준이 된다

Step 3. 화면과 상태 연결

  • {{ count }}는 상태를 화면에 출력한다
  • DOM 조회 코드 없이 값이 표시된다

체크 포인트

  • 출력 대상 DOM을 직접 선택하지 않는다
  • 화면 위치는 템플릿이 결정한다

Step 4. 이벤트와 상태만 연결

  • 버튼 클릭 시 increase() 함수 실행
  • 함수 안에서는 상태만 변경한다

체크 포인트

  • DOM 변경 코드가 없다
  • 상태 변경만으로 화면이 자동 갱신된다

실습 정리

  • Vue에서는 DOM을 직접 조작하지 않는다
  • 상태(State)가 화면의 유일한 기준이다
  • 화면 갱신 책임을 프레임워크가 대신 가진다

5. Vue 상태 → 화면 흐름 체험

실습 목표

  • 입력값, 이벤트, 화면 갱신이 자동으로 연결되는 구조를 체험한다
  • 상태 하나가 여러 화면에 동시에 반영되는 것을 확인한다

실습가이드

📄 파일명: 5-vue-state.html

<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8" />
  <title>Vue 상태 실습 (Composition API)</title>
</head>
<body>

  <div id="app">
    <input v-model="message" />
    <p>{{ message }}</p>
    <p>글자 수: {{ messageLength }}</p>
  </div>

  <script src="https://unpkg.com/vue@3/dist/vue.global.js"></script>
  <script>
    const { createApp, ref, computed } = Vue;

    createApp({
      setup() {
        const message = ref("");

        const messageLength = computed(() => {
          return message.value.length;
        });

        return { message, messageLength };
      }
    }).mount("#app");
  </script>

</body>
</html>

Step 1. 입력과 상태 연결

  • <input>에 v-model을 사용한다
  • 입력값이 자동으로 상태에 저장된다

체크 포인트

  • 키보드 이벤트 코드를 작성하지 않는다
  • 입력과 상태 연결을 Vue가 처리한다

Step 2. 상태 출력

  • 같은 상태를 여러 곳에서 사용한다
  • DOM 접근 코드가 없다

Step 3. 상태 기반 계산 값 (computed)

  • computed()는 상태를 기반으로 한 계산 결과다
  • 상태가 바뀌면 자동으로 다시 계산된다

체크 포인트

  • 계산을 이벤트로 처리하지 않는다
  • 계산 결과도 상태처럼 다룬다

실습 정리

  • 입력, 이벤트, 화면 갱신을 직접 연결하지 않는다
  • 상태 하나가 여러 UI를 동시에 결정한다

6. 서버 데이터 → 화면 출력 (DOM 직접 제어 vs Vue)

Day 3에서 했던 “서버 데이터(posts) 받아서 <ul><li>로 출력”을 Day 4 관점에서 두 방식의 구조 차이로 비교한다.

핵심 메시지

  • DOM 직접 제어 방식: 개발자가 데이터 → 화면을 직접 연결한다 (DOM 생성/초기화/추가까지 모두 작성)
  • Vue 방식: 개발자는 상태(posts) 만 바꾸고, 화면 갱신은 Vue가 담당한다

6-1. DOM 직접 제어 방식 (완성 코드)

📄 파일명: 6-1-dom-posts.html

<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8" />
  <title>DOM - 서버 데이터 출력</title>
</head>
<body>

  <h2>게시글 목록 (DOM 직접 제어)</h2>

  <button id="btn">불러오기</button>

  <ul id="list"></ul>

  <script>
    const button = document.getElementById("btn");
    const list = document.getElementById("list");

    button.addEventListener("click", loadPosts);

    async function loadPosts() {
      const response = await fetch("https://jsonplaceholder.typicode.com/posts");
      const posts = await response.json();

      // 1) 기존 목록 비우기
      list.innerHTML = "";

      // 2) <li> 생성해서 붙이기
      posts.forEach((post) => {
        const li = document.createElement("li");
        li.textContent = post.title;
        list.appendChild(li);
      });
    }
  </script>

</body>
</html>

설명

  • fetch로 데이터를 받아도 화면은 자동으로 바뀌지 않는다

  • 개발자가 직접

    • 목록 비우기 (innerHTML = "")
    • <li> 만들기 (createElement)
    • 붙이기 (appendChild)

    를 매번 작성해야 한다

  • 화면이 커질수록 DOM 조작 코드가 빠르게 늘어난다

6-2. Vue 방식 (Composition API, 완성 코드)

📄 파일명: 6-2-vue-posts.html

<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8" />
  <title>Vue - 서버 데이터 출력 (Composition API)</title>
</head>
<body>

  <div id="app">
    <h2>게시글 목록 (Vue)</h2>

    <button @click="loadPosts">불러오기</button>

    <ul>
      <li v-for="post in posts" :key="post.id">
        {{ post.title }}
      </li>
    </ul>
  </div>

  <script src="https://unpkg.com/vue@3/dist/vue.global.js"></script>
  <script>
    const { createApp, ref } = Vue;

    createApp({
      setup() {
        const posts = ref([]);

        const loadPosts = async () => {
          const response = await fetch("https://jsonplaceholder.typicode.com/posts");
          posts.value = await response.json();
        };

        return { posts, loadPosts };
      }
    }).mount("#app");
  </script>

</body>
</html>

설명

  • 화면에 필요한 구조(<ul><li>...)를 템플릿에서 선언한다 (v-for)
  • 개발자는 DOM을 만들지 않고, 상태(posts)만 변경한다
  • posts.value = ... 한 줄로 상태가 바뀌면, Vue가 화면을 자동으로 다시 그린다

6-3. 이 장의 결론

  • DOM 직접 제어는 “화면을 어떻게 만들지”가 코드의 중심이 된다
  • Vue는 “데이터(상태)가 무엇인지”가 코드의 중심이 된다

그래서 프레임워크는 DOM 조작을 더 잘하려고 나온 게 아니라, DOM 조작을 신경 쓰지 않게 만들려고 나온 것이다

4일차 핵심 정리

  • DOM을 직접 제어할수록 코드와 화면의 연결이 복잡해진다

  • 화면이 커질수록 DOM 관리 비용이 급격히 증가한다

  • 프레임워크는 DOM 변경을 대신 처리해준다

  • 개발자는 DOM이 아니라 상태(State)를 기준으로 생각한다

  • Vue에서 화면은 상태의 결과다

  • 개발자는 어떻게 바꿀지가 아니라 무엇을 보여줄지에 집중한다
